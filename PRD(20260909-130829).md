# Crypto-Tracer --- Product Requirements Document (PRD)

**Project:** Crypto-Tracer\
**SIH Problem Statement:** SIH26182 --- Automated Attribution of Unknown
Cryptocurrency Wallets to Nearest Virtual Asset Service Providers
(VASPs) through Blockchain Intelligence APIs\
**Team:** Cipher\
**Document status:** MVP / SIH Prototype\
**Date:** 2026-09-09

------------------------------------------------------------------------

## 1. Product Summary

Crypto-Tracer is an investigator-focused web platform for cybercrime
cells. An officer provides a suspect cryptocurrency wallet address or
transaction ID plus case metadata. The platform retrieves public
blockchain transaction data, follows relevant fund flows across multiple
wallets, suppresses low-value noise, detects behavioral patterns
associated with custodial exchange deposit addresses, ranks candidate
VASPs with an explainable confidence score, visualizes the path, and
produces an investigator-reviewed evidence dossier and draft legal
request.

The product is **not** an identity-resolution system and does not
autonomously freeze funds.

### Core product promise

> **Wallet → Trace → Explain → Attribute → Evidence → Legal Draft**

The submitted team material defines the product around multi-hop
tracing, relevance-aware pruning, deposit-sweep clustering,
investigator-reviewed notices, and a sovereign/open infrastructure
approach. The MVP should prove that complete journey rather than attempt
every production integration at once.

------------------------------------------------------------------------

## 2. Problem

Investigators may receive only a cryptocurrency wallet address after a
cyber-fraud victim has lost funds. An unhosted wallet does not itself
provide KYC identity. Manual investigation through block explorers
requires repeatedly opening transactions and following addresses.

The team submission identifies the operational bottleneck as tracing
funds from unhosted wallets until they reach a custodial VASP where
legally useful records may exist.

### Problem statement translated into product requirements

1.  Accept a wallet address or transaction ID.
2.  Determine the chain / asset context.
3.  Retrieve relevant transaction history.
4.  Build a directed transaction graph.
5.  Traverse multiple hops.
6.  Remove irrelevant low-value branches.
7.  Identify behavioral evidence around candidate VASP endpoints.
8.  Rank candidate VASPs with explainable confidence.
9.  Preserve transaction-level evidence.
10. Generate an investigator-reviewed report and legal-request draft.

------------------------------------------------------------------------

## 3. Target User

### Primary

-   District cybercrime investigators / cyber cells.
-   Investigating officers conducting cryptocurrency triage.
-   Law-enforcement analysts reviewing transaction evidence.

### Secondary

-   Senior investigators reviewing attribution evidence.
-   Nodal/legal officers preparing requests to service providers.
-   Supervisors reviewing case progress.

The product should be understandable without blockchain expertise: the
UI should emphasize **what happened, where the money went, why an
endpoint is considered a VASP, and what evidence supports the
conclusion**.

## 4. MVP Scope

### P0 --- Must work for the SIH demo

#### Case intake

-   FIR number.
-   Victim name / identifier.
-   Reported loss amount.
-   1930 acknowledgement/reference.
-   Suspect wallet address OR transaction ID.
-   Chain selector, with TRON as the primary MVP chain.
-   Asset selector, with TRC-20 USDT as the primary MVP asset.
-   Investigation notes.

#### Trace

-   Fetch TRC-20 transfer data.
-   Build normalized transaction records.
-   Traverse outgoing fund-flow edges up to configurable depth, e.g. 4
    hops.
-   Apply value-aware branch pruning.
-   Deduplicate transactions and visited addresses.
-   Preserve exact transaction hashes and timestamps.
-   Stop/flag when a branch reaches a known high-risk obfuscation
    boundary.

#### Graph

-   Wallet/account nodes.
-   Transaction edges.
-   Amount and asset on edges.
-   Timestamp.
-   Hop number.
-   Node type: suspect / intermediate / deposit candidate / VASP / mixer
    / bridge / unknown.
-   Zoom, pan, select, expand/collapse.
-   Highlight the strongest path.

#### Attribution

-   Candidate VASP list.
-   Confidence score.
-   Evidence factors.
-   Known-address match if available.
-   Sweep/consolidation evidence.
-   Fan-in evidence.
-   Temporal consistency.
-   Explanation of each factor.

#### Evidence

-   Transaction hashes.
-   From/to addresses.
-   Amounts.
-   Asset.
-   Block/timestamp.
-   Hop sequence.
-   Attribution factors.
-   Data-source provenance.
-   Analysis timestamp.
-   Engine version/configuration.

#### Report

-   Human-readable evidence dossier.
-   Draft Section 94 BNSS record-production request where legally
    appropriate.
-   Explicit investigator review/signature state.
-   No automatic legal order execution.
-   PDF generation.

## 8. Attribution Model

### Principle

**Transaction tracing is deterministic; entity attribution is
inferential.**

If a blockchain transaction says address A transferred 5,500 USDT to
address B, the transaction relationship can be represented directly from
ledger data. Saying that B is controlled by or belongs to a specific
VASP is an inference that must be supported by evidence.

### MVP score

Use an explainable weighted score rather than an opaque ML model:

``` text
confidence =
    0.35 * direct_tag_score
  + 0.35 * sweep_score
  + 0.15 * fan_in_score
  + 0.15 * temporal_score
```

Clamp to `[0, 1]`.

Each component must be stored separately so the UI can answer:

> "Why did the system give this score?"

### Evidence examples

-   Direct verified address/entity tag.
-   Deposit address repeatedly sweeps into a known VASP hot wallet.
-   High fan-in from many deposit addresses.
-   Short temporal gap between deposit and consolidation.
-   Strong consistency across observed transactions.

### Important language rule

Use:

> **"Likely VASP / evidence-backed attribution hypothesis --- 94.2%
> confidence."**

Do not use:

> "This wallet definitely belongs to Binance."

## 9. Trace Algorithm

### Input

-   chain
-   wallet / TxID
-   asset
-   max hops
-   minimum relevant transfer value
-   optional time window

### Algorithm

``` text
resolve input
  ↓
fetch relevant transfers
  ↓
normalize + deduplicate
  ↓
create directed graph
  ↓
BFS from source
  ↓
rank outgoing branches by value/relevance
  ↓
prune dust / low-value noise
  ↓
inspect destination behavior
  ↓
detect sweep/consolidation
  ↓
match candidate VASP registry
  ↓
calculate confidence
  ↓
return graph + evidence + attribution
```

NetworkX supports BFS/DFS traversal and directed multigraph structures,
which maps well to the team's proposed graph model.

## 10. Pruning Rules

The prototype should not blindly discard every transfer below a fixed
dollar threshold in every investigation. Make the rule configurable.

Recommended MVP defaults:

-   `min_relevant_usd = 1.00`
-   `max_hops = 4`
-   `max_nodes_per_hop = configurable`
-   prioritize branches by amount and relevance
-   retain pruned counts for transparency

The UI should show:

> `127 low-value branches suppressed`

rather than silently deleting them.

For forensic reproducibility, store the exact pruning configuration with
every trace.

## 11. Obfuscation Boundaries

### Mixers

If the path enters a known mixer/obfuscation service:

-   stop or limit traversal according to policy;
-   label the node **High-Risk Obfuscation**;
-   preserve the transaction evidence;
-   do not claim successful de-anonymization.

### Privacy coins

For assets such as Monero:

-   treat the chain/asset as outside the MVP tracing capability;
-   flag as a terminal limitation rather than inventing attribution.

### Cross-chain bridges

For MVP:

-   detect/flag a bridge interaction;
-   store the bridge transaction;
-   stop single-chain traversal unless a dedicated cross-chain
    correlation adapter exists.

### Pure unhosted-wallet loops

If funds remain among private wallets without a custodial endpoint:

-   return **No immediate KYC endpoint found**;
-   preserve the strongest path;
-   do not force a VASP attribution.

## 12. Legal/Compliance Product Boundary

The team documents propose Section 94 BNSS as the production notice
mechanism and Section 106 BNSS for seizure. Current legal text is
important here:

-   BNSS Section 94 is a mechanism to require production of
    documents/electronic communications/other things for an
    investigation.
-   BNSS Section 106 concerns police power to seize certain property.
-   Therefore, the product should generate a **draft request/order for
    investigator review**, not represent Section 94 itself as an
    automatic "freeze command".

UI copy should be:

> **Generate Draft Section 94 BNSS Record-Production Request**

and, where the relevant authority/process is applicable:

> **Prepare Seizure/Freeze Evidence Package --- Officer Review
> Required**

The software must never claim that it has frozen an exchange account.

## 13. Evidence Integrity

Every investigation result should include:

-   Case ID.
-   Input address/TxID.
-   Chain.
-   Data-source name.
-   Query time.
-   Raw-source reference/hash where practical.
-   Transaction hash.
-   Block number.
-   Timestamp.
-   Amount and asset.
-   From/to addresses.
-   Hop number.
-   Analysis configuration.
-   Attribution algorithm version.
-   Confidence components.
-   Generated report hash.
-   Report creation time.
-   Investigator review status.

The report should distinguish:

1.  **Observed facts** --- directly obtained from blockchain/source.
2.  **Derived facts** --- computed by the engine.
3.  **Inference** --- attribution hypothesis.
4.  **Investigator action** --- human decision.

## 14. Performance Targets

### SIH MVP targets

-   4-hop demo graph: target under 5 seconds with cached/prepared data.
-   UI graph render: responsive for approximately 100--500 displayed
    nodes.
-   Trace endpoint: asynchronous-ready even if the demo uses a
    synchronous fast path.
-   PDF generation: target under a few seconds for a normal case.

The team's submitted MVP target is sub-5-second graph expansion for
4-hop cases.

Do not present the 5-second number as a guaranteed production SLA until
benchmarked on the final deployment environment.

## 15. Failure States

The UI must explicitly handle:

-   Invalid wallet.
-   Unsupported chain.
-   Unsupported asset.
-   RPC timeout.
-   Rate limit.
-   No transfers found.
-   No relevant path.
-   Maximum-hop reached.
-   Mixer/obfuscator encountered.
-   Bridge encountered.
-   Candidate VASP not found.
-   Low-confidence attribution.
-   Report generation failure.

Example:

``` text
NO KYC ENDPOINT FOUND

The analyzed path remained within unhosted wallets.
No sufficiently supported custodial VASP endpoint was identified.

[View strongest path] [Export evidence]
```

## 16. Demo Dataset Strategy

Use a deterministic demo case matching the submitted narrative:

-   FIR: `2026/812`
-   Victim loss: ₹5,00,000
-   Asset: 5,500 USDT TRC-20
-   Source: suspect wallet
-   Multiple intermediate wallets
-   Final deposit candidate
-   Known VASP hot-wallet destination
-   Confidence around the narrative value only if the actual evidence
    supports it.

**Do not fabricate a real exchange attribution and present it as
real-world fact.**

For the SIH demo, clearly mark synthetic/demo data if the transaction
chain is constructed.

## 17. Acceptance Criteria

The MVP is demo-ready when an evaluator can:

1.  Create a case.
2.  Enter a wallet.
3.  Start a trace.
4.  Watch the system produce a graph.
5.  Inspect at least four hops.
6.  See irrelevant branches suppressed.
7.  Select a candidate VASP.
8.  See confidence and evidence factors.
9.  Inspect transaction hashes/timestamps/amounts.
10. Generate a PDF evidence dossier.
11. Generate a draft legal request.
12. Understand that the final legal action remains human-controlled.

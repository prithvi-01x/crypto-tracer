# Crypto-Tracer --- Architecture

**Status:** SIH MVP architecture\
**Primary chain:** TRON / TRC-20 USDT\
**Pattern:** Modular monolith first; extract workers/services only when
required

------------------------------------------------------------------------

## 1. Architectural Goal

Build a sovereign, explainable blockchain investigation workstation that
turns public ledger data into an actionable investigative lead.

The architecture optimizes for:

-   explainability
-   deterministic evidence
-   fast demo path
-   low infrastructure complexity
-   extensibility to other chains
-   human-in-the-loop legal workflow
-   reproducibility

## 3. Architectural Principle: Modular Monolith

For the SIH deadline, use one deployable backend with strict internal
modules.

Do **not** start with microservices.

Recommended backend modules:

``` text
app/
├── api/
├── domain/
│   ├── cases/
│   ├── transactions/
│   ├── tracing/
│   ├── attribution/
│   ├── evidence/
│   └── reports/
├── adapters/
│   ├── tron/
│   ├── evm/
│   ├── bitcoin/
│   └── vasp_registry/
├── workers/
├── persistence/
├── security/
└── config/
```

This keeps the boundaries needed for future extraction without creating
deployment overhead now.

## 5. Backend Layers

### API layer

Responsible only for:

-   validation
-   authentication/authorization
-   request/response schemas
-   invoking application services
-   status codes
-   API errors

### Application layer

Orchestrates:

-   case creation
-   trace execution
-   attribution
-   evidence collection
-   report generation

### Domain layer

Contains pure business logic:

-   graph construction
-   traversal
-   pruning
-   sweep detection
-   scoring
-   evidence classification

### Adapter layer

Normalizes external systems:

``` text
BlockchainProvider
 ├── TronProvider
 ├── EVMProvider
 └── BitcoinProvider

EntityProvider
 ├── SeedRegistryProvider
 └── FutureOSINTProvider
```

This prevents blockchain-specific API response formats from leaking into
the domain.

## 6. Blockchain Adapter Contract

Every provider should expose a common internal interface.

``` python
class BlockchainProvider(Protocol):
    async def get_transfers(
        self,
        address: str,
        asset: str,
        cursor: str | None = None,
    ) -> TransferPage: ...

    async def get_transaction(
        self,
        tx_hash: str,
    ) -> Transaction: ...

    async def get_block_time(
        self,
        block_number: int,
    ) -> datetime: ...
```

TRON-specific parsing stays inside `TronProvider`.

## 8. Graph Model

Use a directed multigraph internally.

``` text
Node
 ├── address
 ├── chain
 ├── node_type
 ├── labels[]
 ├── first_seen
 ├── last_seen
 └── metadata

Edge
 ├── tx_hash
 ├── from
 ├── to
 ├── asset
 ├── amount
 ├── timestamp
 ├── block_number
 └── source
```

A MultiDiGraph is useful because the same address pair can have multiple
transactions.

NetworkX provides `MultiDiGraph` and BFS/DFS traversal primitives.

## 10. Sweep Detection

The key MVP heuristic:

``` text
deposit_candidate
      │
      ├── receives funds
      │
      ├── holds funds briefly
      │
      └── sends most/all relevant balance
                ↓
         known VASP hot wallet
```

Feature candidates:

-   percentage of balance swept
-   delay from receipt to sweep
-   destination entity confidence
-   number of other deposit addresses feeding destination
-   repeated behavior over time

Example:

``` python
sweep_ratio = swept_amount / relevant_received_balance

sweep_score = weighted(
    ratio=sweep_ratio,
    destination_known=True,
    delay_minutes=...
)
```

Do not hard-code "100% = Binance" as a universal rule.

## 12. Storage Architecture

### PostgreSQL

Source of truth for:

-   cases
-   traces
-   wallets
-   transactions
-   graph edges/nodes
-   attribution results
-   evidence items
-   reports
-   audit events

Use relational columns for frequently queried fields and JSONB for
provider-specific metadata.

PostgreSQL supports JSONB and GIN indexes for structured JSON queries.

### Redis

Use for:

-   API/cache
-   trace status
-   temporary graph/result cache
-   rate-limit coordination
-   Celery broker/result backend if desired

Redis is appropriate for cache and queue/event workloads.

## 13. Worker Architecture

### MVP

A Celery worker can execute:

``` text
trace_wallet
build_graph
run_attribution
generate_report
```

Celery is a task queue designed to distribute work across worker
processes/machines.

For a demo, a synchronous fast path can be retained for tiny/cached
traces.

### Production direction

``` text
API
 ↓
Queue
 ↓
Trace Workers
 ↓
Attribution Workers
 ↓
Report Workers
```

## 14. Cache Strategy

Cache key examples:

``` text
tron:account:{address}:trc20:{cursor}
tron:tx:{tx_hash}
graph:{trace_id}:{config_hash}
vasp:address:{chain}:{address}
```

Cache metadata:

-   fetched_at
-   source
-   expiry
-   request parameters
-   API version

Never treat stale cache as live blockchain state without displaying the
retrieval timestamp.

## 15. VASP Registry

MVP registry should be a versioned local dataset.

``` text
vasp_registry
├── vasp_id
├── name
├── chain
├── address
├── address_type
├── source
├── source_reference
├── confidence
├── valid_from
├── valid_to
└── notes
```

The system should distinguish:

-   verified seed address
-   heuristic candidate
-   analyst-confirmed address

Never silently upgrade a heuristic address into a verified entity.

## 17. Security Architecture

Minimum MVP:

-   HTTPS.
-   Environment variables for secrets.
-   No private keys.
-   No wallet signing.
-   Server-side API keys.
-   Input validation.
-   Request size limits.
-   Rate limiting.
-   Structured logs.
-   Audit trail.
-   Role field even if authentication is mocked.

The system is an investigation tool, not a wallet.

------------------------------------------------------------------------

## 18. Threat Model

### Threat: malicious input

Mitigation:

-   strict address validation
-   request limits
-   max-hop limits
-   max-node limits
-   timeouts

### Threat: API abuse

Mitigation:

-   server-side API keys
-   rate limiting
-   caching
-   provider fallback
-   bounded pagination

### Threat: poisoned entity labels

Mitigation:

-   source provenance
-   registry versioning
-   confidence levels
-   investigator confirmation

### Threat: false attribution

Mitigation:

-   probabilistic language
-   factor-level explanation
-   human review
-   no automatic enforcement

### Threat: evidence tampering

Mitigation:

-   append-only audit records
-   content hashes
-   timestamps
-   immutable report identifiers
-   controlled report generation

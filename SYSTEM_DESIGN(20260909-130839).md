# Crypto-Tracer --- System Design

**System type:** Investigator-facing blockchain intelligence platform\
**MVP:** TRON/TRC-20 USDT\
**Primary workload:** bounded multi-hop transaction tracing +
explainable VASP attribution

------------------------------------------------------------------------

## 1. System Requirements

### Functional

-   case management
-   wallet/TxID ingestion
-   blockchain retrieval
-   graph traversal
-   branch pruning
-   behavioral analysis
-   VASP candidate ranking
-   evidence visualization
-   report generation
-   audit trail

### Non-functional

-   explainable
-   reproducible
-   bounded computation
-   resilient to public API failures
-   evidence provenance
-   human-in-the-loop
-   extensible to multiple chains
-   responsive investigator UI

------------------------------------------------------------------------

If provider-specific JSON needs querying, use targeted PostgreSQL

## 5. Trace State Machine

``` text
CREATED
  ↓
QUEUED
  ↓
FETCHING
  ↓
NORMALIZING
  ↓
TRAVERSING
  ↓
PRUNING
  ↓
ATTRIBUTING
  ↓
EVIDENCE_BUILDING
  ↓
COMPLETED
```

Failure:

``` text
any state → FAILED
```

Partial result:

``` text
TRAVERSING → PARTIAL
```

Examples:

-   provider rate limit
-   bridge boundary
-   mixer boundary
-   max-hop boundary
-   provider timeout

A partial trace should still be exportable as evidence.

## 6. Traversal Algorithm

### BFS

Use BFS because the investigation is naturally hop-oriented:

``` text
source = suspect wallet

depth 0 → suspect
depth 1 → direct recipients
depth 2 → recipients of recipients
depth 3 → ...
depth 4 → ...
```

NetworkX documents BFS traversal and depth limits.

### Pseudocode

``` python
queue = deque([(source, 0)])
visited = {source}

while queue:
    address, depth = queue.popleft()

    if depth >= max_hops:
        continue

    transfers = fetch_relevant_transfers(address)

    for tx in transfers:
        if tx.to_address in visited:
            continue

        relevance = calculate_relevance(tx)

        if relevance < threshold:
            record_pruned(tx)
            continue

        add_edge(address, tx.to_address, tx)

        visited.add(tx.to_address)
        queue.append((tx.to_address, depth + 1))
```

## 7. Relevance Score

Start simple.

``` text
relevance =
    amount_weight
  + asset_match
  + temporal_relevance
  + path_relevance
  + destination_relevance
```

For a TRC-20 USDT investigation, an asset match should dominate over
unrelated TRX gas activity.

Example:

``` python
if asset == target_asset:
    asset_score = 1.0
else:
    asset_score = 0.0
```

------------------------------------------------------------------------

## 8. Dust Filtering

The team proposal uses `< $1` as the MVP dust threshold.

Implement:

``` python
if usd_value < config.min_relevant_usd:
    prune(reason="DUST")
```

But retain:

-   transaction hash
-   amount
-   reason
-   threshold
-   trace configuration

This preserves reproducibility.

------------------------------------------------------------------------

## 9. Sweep Detection

For each candidate deposit address:

``` text
received relevant funds
       ↓
calculate balance relevant to trace
       ↓
find outgoing transfers
       ↓
identify dominant destination
       ↓
calculate sweep ratio
       ↓
inspect destination entity
```

Example:

``` python
sweep_ratio = outgoing_to_destination / relevant_received

if sweep_ratio >= 0.90:
    strong_sweep_signal = True
```

The threshold is a heuristic, not proof of ownership.

------------------------------------------------------------------------

## 10. Fan-In Detection

For candidate VASP hot wallet:

``` text
address A ─┐
address B ─┤
address C ─┼──> candidate hot wallet
address D ─┤
address E ─┘
```

Compute:

``` python
fan_in_count = distinct_sender_count(
    destination=candidate
)
```

Normalize against configured observation window.

High fan-in supports---but does not prove---an omnibus consolidation
interpretation.

------------------------------------------------------------------------

## 11. Temporal Signal

Measure:

``` text
deposit received
      ↓
time to sweep
```

Possible feature:

``` python
temporal_score = exp(-delay_hours / tau)
```

where `tau` is configurable.

This avoids hard-coding a universal "2 hours means exchange" rule.

------------------------------------------------------------------------

## 12. Attribution Scoring

``` python
confidence = (
    0.35 * direct_tag_score +
    0.35 * sweep_score +
    0.15 * fan_in_score +
    0.15 * temporal_score
)
```

Store all component values.

### Confidence bands

Suggested UI:

``` text
0.00–0.49  LOW
0.50–0.74  MODERATE
0.75–0.89  HIGH
0.90–1.00  VERY HIGH
```

These are product display bands, not legal certainty.

## 16. Idempotency

Trace requests should support an idempotency key.

``` http
Idempotency-Key: case_01-trace-hash-config-v1
```

Equivalent trace requests should reuse a completed/cached result where
safe.

This prevents accidental duplicate expensive provider calls.

------------------------------------------------------------------------

## 17. Rate-Limit Strategy

``` text
request
 ↓
cache lookup
 ├── hit → return
 └── miss
      ↓
provider
      ↓
store normalized result
      ↓
cache
```

Use:

-   exponential backoff
-   bounded retries
-   provider timeout
-   request concurrency limit
-   pagination
-   local caching

Do not solve public API rate limits by endlessly rotating credentials or
violating provider terms.

------------------------------------------------------------------------

## 18. Demo Reliability

The demo path should support:

``` text
LIVE
 └── real public blockchain data

REPLAY
 └── stored normalized trace fixture
```

A visible developer/demo toggle can select the mode during development,
but the judge-facing UI should simply say:

> **Blockchain analysis complete**

Do not fake a live response while claiming it is live.

For MVP, enforce:

``` text

max_nodes = 500

```

## 21. Future Scaling

If graph sizes become too large:

``` text
PostgreSQL
    ↓
graph projection / specialized graph store
```

Potential future options:

-   Neo4j
-   Memgraph
-   analytical column store
-   distributed graph processing

Do not introduce a graph database solely for the SIH prototype.

EVIDENCE_READY
      ↓

      ↓
INVESTIGATOR_REVIEW

      ↓

## 23. Final System Invariant

The most important invariant:

> **Every attribution shown to an investigator must be explainable
> through stored evidence and reproducible analysis configuration.**

No black-box "AI says Binance" result.

    documentation and account/transaction interfaces.

-   ReportLab provides Python PDF generation.
